# Отчёт: Система знаний команды

## Название выбранного проекта

Система знаний команды (поиск по своим данным + память)

## Ценность (для кого и зачем)

Новичкам, менеджерам и тимлидам: быстрые ответы по внутренним материалам с цитатами-источниками; если данных нет — честная ручная проверка вместо выдуманного ответа.

## 3 сценария пользователя

1. Пользователь загружает документы → они появляются в витрине.  
2. Пользователь задаёт вопрос → получает ответ и цитаты-источники.  
3. Вопрос без опоры в базе → `needs_review=true`, «данных недостаточно», причина в истории/аудите.

## Точки доступа API

- `POST /kb/documents`
- `GET /kb/documents`
- `POST /kb/ask`
- `POST /ai/answer_with_sources`
- дополнительно: `GET /kb/documents/{id}`, `GET /qa/runs`, `GET /audit/runs`, `GET /export/qa`

## Схема данных (таблицы)

- `documents` — id, created_at, title, text  
- `snippets` — id, created_at, document_id, snippet_text  
- `qa_runs` — id, created_at, question, answer, sources_json, needs_review, error  
- `audit_runs` — id, created_at, action, input, output, status, error, duration_ms  

## ИИ-операция

### Схема JSON

```json
{
  "answer": "string",
  "sources": [{"quote": "string"}],
  "confidence": "high|medium|low",
  "needs_review": true
}
```

### Температура

`0.1` (низкая, для стабильного формата)

### Когда нужна ручная проверка

- нет подходящих фрагментов;
- `confidence=low`;
- пустые `sources`;
- ошибка парсинга/вызова LLM.

## Память/контекст

Документы режутся на абзацы (`snippets`). По вопросу выполняется keyword-поиск top-K фрагментов; они передаются в LLM как context. История вопросов хранится в `qa_runs`.

## Контроль качества

- вход: непустые title/text/question, лимиты длины;  
- выход: валидация Pydantic-схемой; пустые sources → `needs_review=true`;  
- каждый ключевой запрос пишется в `audit_runs`.

## План внедрения за 1 день

1. Поднять сервис по README / Docker.  
2. Загрузить актуальные 5–20 внутренних документов.  
3. Прогнать 10 контрольных вопросов.  
4. Показать операторам вкладку «требует проверки».  
5. Настроить `LLM_API_KEY` и проверить 3 curl из README.

## Мини-экономика

| | До | После |
|---|----|-------|
| Время на 1 типовой вопрос | ~15 мин (поиск по файлам/людям) | ~1–2 мин (панель + проверка цитат) |
| 100 операций | ~1500 мин (~25 ч) | ~150–200 мин (~3 ч) |
| Ценность | Повторяющиеся ответы «из головы» | Единая точка правды + аудит + меньше домыслов |

Оценка «на салфетке»: экономия порядка 20+ часов на 100 однотипных вопросах онбординга/поддержки.

## Риски и меры снижения (минимум 5)

1. Галлюцинации LLM → ответ только по context + строгий JSON + needs_review.  
2. Утечка секретов → `.env`, `.gitignore`, запрет секретов в документах/README.  
3. Пустая база → честный «данных недостаточно», без вызова LLM.  
4. Нестабильный формат модели → Pydantic-валидация + fallback review.  
5. Потеря воспроизводимости → Docker, seed-скрипт, tests_data, README ≤ 10 мин.  
6. Слепое доверие offline-режиму → в ответе пометка offline, цитаты обязательны.

## 3 строки для портфолио

Проблема: знания команды разбросаны, ответы повторяются и часто додумываются.  
Решение: веб-система с поиском по своим документам, строгим JSON и ручной проверкой.  
Результат: ответы с источниками, история QA, аудит запусков, запуск по README/Docker.

## Сложности и как решал(а)

- Нужна работа без ключа LLM для воспроизводимости → offline extractive-режим.  
- Связка цитат модели с `document_id` → сопоставление quote с найденными snippets.  
- Обязательный аудит при уже закоммиченных доменных записях → отдельная запись `audit_runs` после операции.

## План развития

- Векторный поиск / гибрид keyword+embeddings.  
- Роли и доступ к документам.  
- Загрузка файлов (PDF/Markdown) вместо только raw text.  
- Кнопка «подтвердить/исправить» для needs_review с обратной записью в базу.
